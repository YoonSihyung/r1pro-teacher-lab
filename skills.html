01 / 상태를 바꿔 보세요

개념도는 pick을 “목표 물체를 잡음”, place_on을 “목표 지지면 위 + grasp 해제”로 판정합니다. 실제 평가는 해당 instance의 bddl_goal을 따릅니다. 안정적으로 놓였는지 추가 검사하는 조건은 별도로 설계할 수 있습니다.

02 / LABEL

라벨은 긴 데모를 잘라내는 인덱스입니다.

사진 속 pick·place_on 개수는 이런 시간 구간을 모아 셀 수 있습니다. 구간을 골라내는 것과 환경을 복원하는 것은 별도 작업입니다.

이동0–300
pick300–480
이동·운반480–900
place_on900–1080
다음 skill1080–1200

프레임 번호와 물체는 설명용 가상 예시입니다. 실제 annotation의 시간 기준·경계 규칙에 맞춰 데이터와 정렬해야 합니다.

BC에는 구간 내부의 정답 행동

(관측 sₜ, 데모 행동 aₜ)을 꺼내서 policy의 행동을 데모에 맞춥니다. pick policy는 pick 구간, place_on policy는 place_on 구간으로 학습합니다.

Teacher 입력에 객체 상태·목표 정보를 추가한다면, 데모에도 같은 정보를 준비해야 합니다. 라벨만으로 새로운 privileged 정보가 자동 생성되지는 않습니다.

RL에는 구간 시작의 환경 상태

place_on 예시에서는 프레임 900 직전의 상태를 복원합니다. 이후 데모의 행동을 정답으로 재생하지 않고, 현재 policy가 새 행동을 실행합니다.

새 rollout의 step 번호와 원래 데모의 프레임 번호는 서로 다릅니다. policy가 빨리 성공하거나 실패해도 환경의 실제 결과를 평가합니다.

03 / SNAPSHOT

사진 한 장이 아니라, 다시 실행할 수 있는 상태입니다.

컵의 위치만 복원하면 place_on 시작 상태가 완성되지 않습니다. 로봇 관절과 그리퍼 상태, 잡고 있는 물체와의 관계도 맞아야 합니다.

Place_on의 시작 전제조건

  • 정해진 물체를 로봇이 실제로 잡고 있음
  • 목표 지지면이 존재하고 객체 매핑이 맞음
  • 물체가 이미 성공 상태에 있지 않음

컵이 손 근처에 떠 있어도 grasp 관계가 복원되지 않으면 실행 직후 떨어질 수 있습니다. 위 그림에서 “grasp 복원 실패”를 선택해 차이를 보세요.

복원한 뒤에 물리 상태를 확인해야 합니다.

공개 evaluator는 assisted grasp와 관절 구동 목표를 복원하고, 행동 명령 없이 25번 물리 안정화 step을 진행합니다. 이후 step 0의 goal을 검사하고 policy를 실행합니다. 25는 이 평가 구현의 설정이며 모든 RL 환경의 필수값은 아닙니다. [2]

04 / SUCCESS & REWARD

“라벨에 place_on이라고 쓰여 있음”은 실행 성공이 아닙니다.

라벨은 데모 구간의 이름입니다. 새 policy가 실제로 성공했는지는 실행 후 환경 상태에서 검사합니다.

pick의 개념적 예
목표 물체를 잡고 있는가?

그리퍼를 닫았는지만 검사하면 빈손으로 닫아도 성공 처리될 수 있습니다.

place_on의 개념적 예
목표 물체가 목표 지지면 위에 있는가?
필요하면: grasp를 해제했는가?

다른 테이블에 놓거나 손에 든 채 목표 위로 가져가는 것과 구분합니다.

BEHAVIOR-Skill YAML에는 skill별 bddl_goal이 있습니다. 대상 객체를 시뮬레이터 객체에 연결해 검사합니다. 위 예시는 설명용이며, 배포된 goal을 임의로 바꾸면 같은 평가가 아닙니다.

Success · 완료 판정

참/거짓 결과로 skill 종료와 성공률을 계산합니다. 공개 evaluator는 매 step goal을 검사하며, 성공하거나 기록된 데모 길이의 두 배에 도달하면 종료합니다. [2]

Reward · 학습 신호

성공 시 보상을 주는 것부터 시작할 수 있습니다. 접근 거리, 목표 방향으로의 진행, 시간 비용 같은 중간 보상은 RL용으로 추가 설계할 수 있습니다.

성공 조건이 제공된다고 dense reward와 PPO 학습 환경까지 완성된 것은 아닙니다. 검증 기준과 학습 보상은 구분해서 연결합니다.

05 / YOUR FIVE TASKS

두 teacher를 만드는 데이터 흐름

다섯 태스크에서 같은 skill을 모으되, 각 instance의 대상 객체와 시작 상태를 유지합니다.

BC · 지도학습
  1. 다섯 태스크의 데모를 학습·평가 episode로 분리
  2. 라벨로 pick / place_on 구간 선택
  3. 관측·목표·데모 행동을 공통 형식으로 변환
  4. 각 Gaussian actor를 데모 행동에 맞춰 초기화
결과: 의미 있는 동작으로 시작하는 actor
RL · 환경 상호작용
  1. 학습용 skill instance와 시작 상태 선택
  2. snapshot 복원·안정화·시작 전제조건 확인
  3. 현재 actor로 행동하고 새 관측·reward 수집
  4. skill goal 검사, PPO로 actor·critic 개선
결과: 실제 성공 보상으로 개선한 teacher

제공 범위의 중요한 차이

모든 라벨에 시작 snapshot이 붙어 있지는 않습니다.

10,000전체 데모의 skill annotation
500평가용 데모의 goal + 시작 상태50태스크 × 태스크당 10개

공개 데이터 카드에서 시작 상태와 평가 설정은 평가 subset에만 제공됩니다. 원하는 다섯 태스크의 해당 instance와 파일을 확인해야 합니다. [1]

권장 구성: 학습 episode의 원본 simulator 기록에서 skill 시작 상태를 복원해 별도로 저장하고, 그 상태로 RL을 학습합니다. 평가 episode와 snapshot은 성능 측정에 유지합니다.

상태 생성 pipeline은 공개 Behavior-Skill 저장소에 포함되지 않습니다. 원본 데모와 환경 버전에 맞춰 구성해야 합니다. 평가용 snapshot을 학습에 사용했다면 동일 subset의 결과는 독립 평가 성능이 아닙니다. [2]

실제 운영에서는 앞 skill의 오차도 고려합니다.

처음에는 데모의 정상 시작 상태에서 skill을 익히고, 이후 객체·로봇 pose의 작은 변화와 이전 policy가 만든 상태를 학습에 섞을 수 있습니다. 초기 grasp와 충돌 상태가 유효한 범위에서 변화시켜야 합니다. 이 부분은 제안하는 학습 설계입니다.

출처와 예시의 범위

그림의 물체·프레임·동작은 설명용입니다. 제공 파일을 실제로 복원하거나 teacher 학습을 실행한 결과가 아닙니다. 공개 파일 형식과 복원 절차는 아래 문서 기준입니다.

  1. Behavior-Skill 데이터 카드 — annotation, evaluation goal, snapshot 형식과 제공 범위
  2. Behavior-Skill 공식 코드 — 상태 복원·안정화·성공 검사 절차와 저장소 범위
  3. 원본 BEHAVIOR-1K simulator 기록 — 학습 episode의 상태 복원을 위한 원본 데이터

확인일 2026-10-07. 공개 snapshot은 OmniGibson 3.7.2 기반이므로 복원 환경의 버전도 맞춰야 합니다. [1]

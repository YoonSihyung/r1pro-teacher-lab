01

LEARNING PIPELINE

데이터에서 배포 모델까지.

같은 흐름을 pick과 place_on에 각각 적용합니다. SGS는 학습 시작 상태를 고르는 sampler입니다.

BC 초기화와 코드 정렬은 역할이 다릅니다.

BC는 모델의 가중치를 준비합니다. 코드 prepare는 로봇의 물리적인 시작 상태를 준비합니다. RL에서는 demo를 계속 replay에 섞고, 코드가 실제로 만드는 handoff 상태에서 연습합니다.

왜 snapshot을 저장하나요?

코드가 센서 gate를 통과한 상태에서 빠르게 reset해 정밀 skill을 반복 연습하기 위해서입니다. 배포 때는 같은 코드로 다시 접근합니다.

왜 DAgger가 필요한가요?

Student가 스스로 움직이며 방문한 상태를 teacher에게 다시 라벨링합니다. 사람이 개입하지 않고, 단순 teacher trajectory 모방에서 생기는 분포 차이를 줄입니다.

02

CURRENT MODEL / ACTUAL IMPLEMENTATION

Teacher는 MLP. 현재 student는 CNN+GRU.

입력에 맞춰 구조를 나눕니다. Teacher의 숫자 state를 처리하는 MLP와 시각 policy의 encoder는 서로 다른 역할입니다.

Teacher가 쉬운 문제부터 풉니다.

센서 feature 83D에 시뮬레이터 정답 정보 24D를 더합니다. 256×256 Gaussian MLP와 Q ensemble로 local 동작을 학습합니다.

Student에는 정답 입력이 없습니다.

Teacher 행동을 타깃으로 받되 RGB·proprio·추정값만 입력합니다. 현재 CNN+GRU는 기준선이고, pretrained encoder + 작은 Transformer는 아래의 확장안입니다.

03

DEPLOYMENT / ONE EXECUTION PATH

실배포는 student만 교체해서 실행합니다.

시작 pose를 정확히 같게 강제하기보다, 코드가 남기는 추정·정렬 오차 범위에서 policy가 작동하도록 학습합니다.

전신 상태를 맞추고, local 단계에서는 유지합니다.

손목만 정렬하는 구조가 아닙니다. 접근 단계는 전신을 쓰고, policy 단계에서는 선택한 팔·그리퍼만 움직입니다. 코드·student·배포 성공 gate 모두 센서 입력을 쓰며, 정답 물체 pose는 teacher와 학습 reward·평가 경로에서만 사용합니다.

04

RECOMMENDED EXTENSION / NOT IMPLEMENTED

두 expert에서 하나의 goal-conditioned policy로.

지금은 단순한 기준선을 검증하고, 공유 encoder·Transformer로 확장합니다. 이 그림은 구현 완료가 아닌 제안입니다.

1

두 expert를 먼저 검증

동일한 입력·8D action 계약으로 pick / place_on teacher를 학습합니다.

2

공유 student로 증류

skill·task별 데이터를 균형 있게 섞고 goal·물체 역할을 명시합니다.

3

필요한 확장만 실험

Visual RL·FQL·전신 action은 각각 구현과 비교 검증을 거쳐 추가합니다.

한 local policy로 두 skill을 처리하는 것과 전체 태스크를 끝까지 수행하는 것은 범위가 다릅니다. 장기 순서 결정은 상위 실행기가 담당합니다. 그림의 추천 모델 크기는 비교를 시작할 기준이며 R1Pro에서 측정된 최적값이 아닙니다.
